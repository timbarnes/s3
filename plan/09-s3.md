# 09. s3: the compiler in Scheme only

Written 2026-10-13. s2 froze at P13 (tag `s2-final`) with two compilers,
one in Rust and one in Scheme, which produce the same code byte for byte.
s3 is a clone of s2, with its history, that keeps only the compiler in
Scheme. Its phases are numbered S0, S1, and so on.

## S0. The Rust compiler goes

Done 2026-10-13. Five steps, as P13.6 and 08 (C5 b) decided:

1. **The Rust compiler is deleted**, along with everything gated behind
   the `rust-compiler` feature: `expand.rs`, `analyze.rs`, `codegen.rs`,
   most of `syntax_rules.rs` (the matcher), the Rust import resolution
   in `libraries.rs`, `pending_load`, `S2_COMPILER` and its round-trip
   mode, the oracle and fixed-point tests (`tests/compiler.rs`) and
   `tests/no-rust.sh`. Also the placeholders that existed only so both
   builds made the same images: `%compiled-library`, `%load-then-eval`,
   and the VM's special path for `eval`. `eval`, `dis` and
   `%load-library` are now plain primitives that hold their cells until
   the compiler's image rebinds them at startup.
2. **The boot images are committed**, in `boot/`, and built into the
   binary with `include_bytes!`. The cache next to the executable is
   gone. `S3_CORE_IMAGE` and `S3_COMPILER_IMAGE` still name other image
   files to start from.
3. **`scripts/rebuild-images.sh`** remakes them. Each round compiles
   `core.scm` and the compiler using the images the previous round made,
   until a round changes nothing, and then builds s3 again with the new
   images embedded. A test (`boot_images_reproduce_themselves`) fails if
   the committed images are stale or don't reproduce themselves.
4. **A verifier** (`src/vm/verify.rs`) checks every template made from
   data (`%make-template`) or read from a compiled file. Before P12's
   fixed stack, it wasn't needed; 08 listed it as a risk to address if
   the Rust compiler went.
5. **s2 is renamed s3** everywhere outside `plan/`: the crate and the
   binary, the `S3_*` environment variables, `.s3o` files, the
   compiled-file magic, the `(s3)` and `(s3 compiler)` libraries, the
   `s3` feature identifier and the prompt. `plan/` is s2's history and
   keeps its name.

### The verifier

It follows the stack depth through each template's code, counted from
the frame's first parameter, and checks that:

- every local an instruction names (`LocalRef`, `LocalSet`, `MakeBox`,
  `PatchFree`, `CarLocal`, `CdrLocal`) is below that depth;
- no instruction pops past the frame;
- every instruction is reached at only one depth;
- the code never runs off its end;
- a `SelfTailCall` passes as many arguments as there are parameters.

It also does the operand checks `%make-template` already did: constants
exist and are of the right kind, jumps land inside the code, and
free-variable indexes and names agree. The fasl loader did none of
these before (P11). Pushes needed no new check, since the dispatch loop
already bounds them.

All the code the tests, chibi's suite, the r7rs benchmarks and the boot
images compile to passes. Startup, which now verifies both images, is
3.8ms against s2's 3.7ms in Scheme mode, within the noise.

### Bootstrapping

The images are compiled from `scheme/` by the compiler in Scheme, which
itself runs from the previous images. A change to `scheme/` takes
`scripts/rebuild-images.sh`, and usually reaches a fixed point in one to
three rounds.

**A change the old images can't survive** (the instruction set, the
compiled-file format, or a primitive the old compiler's image calls)
needs a binary that still reads the old images while compiling the new
ones. The rename was one: the magic and the library names changed. It
was bootstrapped by patching the old images, swapping `s2fasl` for
`s3fasl` and the length-prefixed name `s2` for `s3`, as seeds. The first
rebuild round then reproduced them exactly, so the committed images are
the compiler's own output and nothing in them is a patch. As a last
resort, `s2-final` builds with the Rust compiler.

### Decisions

- **The large Rust stack stays.** 08's risk table said the 1GB session
  thread could go with the Rust compiler. It can't: the reader, the
  printer, `equal?` and the compiled-file writer still recurse in Rust.
  Without it, s3 aborts reading or printing a list nested 100,000 deep,
  which s2 handles. Its comment now says why.
- **Images are embedded, not cached next to the executable.** The binary
  stands alone, and a stale image is a failed test, not a silent rebuild
  at startup.
- **`(s3)` replaces `(s2)`** with no alias. Nothing outside this
  repository imports it.

## S1. A faster compiler (in progress)

Planned 2026-10-13; steps 0 and 1 done the same day. P13.6 measured compiling in Scheme at 8-10 times
slower than s2's Rust compiler. That shows in the REPL and in a library
file's first load; cached loads, startup and run time are unaffected.

### What the profile shows

Compiling 1,000 one-line definitions (a named `let` and a `cond`) takes
about **56,000 VM instructions and 6,300 calls per definition**: far
more than the work needs. Counted per procedure:

- **About a third is `syntax-rules` matching**, mostly `cond`'s
  expansion: `ellipsis?`, `identifier?`, `match-pattern`, `literal?`,
  `match-sequence` and `strip`.
- **A fifth of all instructions are `GlobalRef`**, the compiler fetching
  its own top-level procedures before calling them. Record accessors
  such as `transformer-literals` are full calls.
- **Scope lookup** (`resolve`, `find`) is about 8%.

As a check: `ellipsis?` turned every pattern identifier into a fresh
string to compare it with `"..."`. Comparing the symbol with `eq?`
instead took the 1,000 definitions from 289ms to 270ms, 7%.

### Steps, cheapest first

0. **Measurement.** The per-procedure profile kept under
   `--features stats`, and `bench/compile.sh` for the three cases P13.6
   measured: the REPL, `--compile` of chibi's suite and
   `--compiler-image`. **Target: 3 times faster**, about 3 times slower
   than s2's Rust compiler.
1. **Waste in the compiler**, in Scheme only: string comparisons in
   `ellipsis?` and `underscore?`; `macro->transformer` rebuilding a
   record from `%macro-parts` at every macro use; `resolve` doing a
   `list-tail` over the frames at every lookup; the linear search that
   deduplicates constants; the `memv` sets in analysis, quadratic in a
   large body.
2. **The common derived forms in the expander** (`cond`, `case`, `and`,
   `or`, `when`, `unless`, `let*`, `do`) instead of through
   `syntax-rules` in `core.scm`. Probably the largest single step. It
   costs code in `expand.scm`, and the golden listings may change where
   variables are numbered differently: checked once and accepted, since
   nothing has to match the Rust compiler any more.
3. **Better code from the compiler, so it compiles itself faster.** A
   library's top-level definition that is never `set!` is a constant:
   references to it can skip the cell, calls to it become known calls,
   and record accessors and small procedures can be inlined. This
   overlaps the optimisations below, and makes every program faster,
   not only the compiler.
4. **Hot primitives in Rust**, if they still show after that: `strip`,
   `identifier?`, frame lookup.
5. **Hash tables** for frames and constant pools, only if lookups still
   dominate.

Each change takes `scripts/rebuild-images.sh`. The fixed-point test
catches a compiler that breaks itself, the verifier catches bad code
before it runs, and the golden tests show any change in the code
generated. Steps 1 and 2 change only the compiler; step 3 changes the
code it generates for every program.

**Estimate**, before measuring: 2-4 times from steps 1-3.

### Steps 0 and 1, done

**Measurement.** `--features stats` now also prints the 40 procedures
that ran the most instructions, with the calls each made, labelled by
name and locals (`loop (rest items)`) so the named lets can be told
apart. A template's counts are keyed by its address, checked against
its name's allocation, so one collected and its address reused starts
afresh. `bench/compile.sh` times the three cases, or compares two
binaries with `--compare`.

**Waste removed**, each measured on its own:

| Change | What it removed |
|---|---|
| `ellipsis?`, `underscore?` compare symbols with `eq?` | a fresh string per identifier tested |
| Patterns analysed at definition: each rule stores a matcher, a tagged vector with the ellipsis position, counts and repeated variables worked out | every use re-scanning every pattern with `list-parts` and `ellipsis?`, and recomputing `pattern-vars` |
| Templates analysed at definition the same way: pattern variables, plain identifiers, and `sub ...` with its depth and variables | every use re-counting ellipses and recomputing `template-vars` |
| `free-variables` memoised per form; a nested lambda counts as its free variables | walking each nested lambda again at every level, and twice for a lambda group's members |
| Each frame holds its bindings consed onto those of the frames around it | a Scheme loop over frames, an `assq` each; now one `assq` |
| Constants found through an alist from constant to index | a linear search through the pool, three accessor calls per element; 40% of `--compiler-image` |

None changes the code generated. Chibi's suite disassembles to the
same 19,357 lines as before S1, and a file of definitions compiles to
the same bytes. Compiled files differ where they hold macros, whose
rules are now matchers and compiled templates.

Patterns and templates change what a macro holds, so the old images'
macros couldn't be read by the new matcher. Each change was
bootstrapped in two steps: first, `macro->transformer` converted
old-format rules when a macro was used, until a rebuild reached a
fixed point; then the conversion was removed and the images rebuilt.

**Results**, `bench/compile.sh --compare` against S0, medians of 7:

| | S0 | after step 1 | |
|---|---:|---:|---:|
| REPL, 1,000 definitions | 292ms | 193ms | 1.51x |
| `--compile` chibi's suite | 123ms | 88ms | 1.41x |
| `--compiler-image` | 75ms | 48ms | 1.57x |

Instructions per definition in the REPL case went from about 56,000 to
35,000. **Left of step 1:** the `memv` sets in analysis and the record
`macro->transformer` makes per use are each a few percent at most.
`GlobalRef` is still 19% of all instructions, and that is step 3's
territory.

**Next: step 2**, the derived forms in the expander.

## What follows

Left to s3 at P13.6, besides S1:

- **Optimisations in Scheme** that C7 ruled out while the two compilers
  had to agree: constant folding, inlining known procedures, and better
  `letrec`.
- **Procedural macros:** explicit renaming or `syntax-case`. The
  expander in Scheme makes them possible (08, C4).
- **Hash tables** (SRFI 69 or 125).
- **More libraries.**
- **Recursion in Rust over data** (reader, printer, `equal?`, fasl),
  made iterative, if the large stack is ever to go.
